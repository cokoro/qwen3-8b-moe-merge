# 下一轮实验方案：4×H100 80GB 上把「强专家 → MOPD」完整做一遍

## 1. 为什么本轮大部分分数是 0：算力限制了评测设置，融合方式决定了能力能不能保住

**算力造成的地板（有数据支撑的部分）**
- Qwen3-8B 每个 token 的 KV 缓存约 144KB（36 层 × 8 个 KV 头 × 128 维 × K/V × bf16）。
- 本轮 TB2 跑在 1 张 L40S 48GB 上，KV 池大约只能放 14.5 万 token；而 12 并发、每题上下文最多 28K，最多需要约 34 万 token。请求排队，推理变慢，base 在 74 题里有 41 题 agent 超时。
- 为了放进显存，评测的上下文只开了 32K（模型卡是 256K），单步输出只开了 4096（模型卡是 80K），TB2 只跑了 1 次（要求 5 次）。SWE 有多次因为超出 32K 上下文而中断。
- DGX Spark 的内存带宽只有 273GB/s（H100 是 3.35TB/s），生成慢，同样会造成超时。

**不是算力造成的部分（如实说明）**
- ASI 修正评测环境后，所有模型仍在地板上（60 题最多 2 题拿到部分分）。
- SWE 修复 harness 后，base 提交的补丁本身就有编译 / 运行错误。
- 第一版终端 / SWE 专家的训练格式与评测 agent 不匹配。
- 这些要靠更好的数据和更强的专家来解决，不是靠加卡。

**融合方式决定能力能不能保住（本轮的核心发现）**
- 权重融合会产生任何单个专家都没有的病态行为：TIES 让终端专家「接管」了 40% 的 HLE 回答（输出 bash 代码而不是答案）；Linear 有 27 次把 prompt 模板原样抄回来。
- MOPD 学生没有出现这类问题（0 次代码块回答，0 次抄模板），格式完整度和 base 持平。
- 分数上 MOPD 没拉开，是因为教师本身不比 base 强。文献也一致指出：MOPD 的收益 = 学生追回的「教师 − 学生」差距，差距为 0 时收益也为 0。

## 2. 为什么 MOPD 比权重融合更强（机制与文献，详见 `mopd_literature.md`）

1. **在输出分布上整合，而不是在参数上做算术。** 融合假设不同专家的参数增量可以线性叠加；网络是非线性的，增量之间会互相干扰、抵消，而且对系数非常敏感。小米 MOPD 论文（Qwen3-30B-A3B）：MOPD 0.937，Task Arithmetic 0.857，权重平均 0.328。
2. **按输入路由教师。** 每个 prompt 由所属领域的教师逐 token 监督，领域冲突交给梯度去解决。融合对所有输入都用同一组参数，没有「看输入」的能力。
3. **On-policy 纠错。** 学生在自己生成的回答上学习，错在哪里就在哪里被纠正，消除了离线训练的暴露偏差（GKD）。
4. **稠密信号，成本低。** Qwen3 技术报告中，Qwen3-8B 做 on-policy 蒸馏只用 1,800 GPU·h 就到 AIME'24 74.4，而 RL 用了 17,920 GPU·h 只到 67.6。
5. **反向 KL 是 mode-seeking 的。** 学生会稳定地采用教师的主模式，格式不会摇摆，这正对应本轮 MOPD 的格式完整性。
6. **不要求同结构、同大小，教师数量几乎没有上限。** 可以用多个小专家去教一个更大的学生。DeepSeek-V4 用了 10 个以上教师，以此取代混合 RL；Kimi K3 用了 9 个教师；MiMo-V2-Flash 明确选择「不合并参数」。
7. **前提条件。** 教师需要和学生同源，而且要显著强于学生；在指令模型、近似正交的任务向量这些条件下，融合也可以做得很好（MergeBench、AppWorld）。所以下一轮的第一步是先把教师训强。

## 3. 训练方案（大方向）

| 阶段 | 做什么 | 关键设置 | 通过标准 |
|---|---|---|---|
| A. 训强专家 | HLE：拒绝采样自蒸馏，用 Qwen3-8B thinking 模式或更大的同源教师，在非 HLE 的高难推理题上生成并过滤正确答案，输出成「Explanation / Answer / Confidence」格式。ASI：科学计算代码数据，在任务声明的环境里执行，只保留跑通的。TB2：terminus-2 多轮轨迹（本轮的 `terminal_v2` 数据）。SWE：mini-swe-agent 工具调用轨迹（本轮的 `swe_v2` 数据）。全部做去污染。 | LoRA r64 或全参；序列 32K；每个专家约 2–4 h（4×H100） | 每个专家在**自己的** benchmark 上，配对 bootstrap CI **显著高于** base |
| B. 基线融合 | Linear、TIES；在**生成式**开发集上扫系数 / 密度（不能用 teacher-forced loss 选模型） | 每个配置约 0.1 GPU·h | 作为对照 |
| C. MOPD | 4 个教师全部纳入，按领域路由；先用教师生成、过滤后的数据做 SFT 预热，再做 on-policy 蒸馏（on-policy 比例 ≥ 25%）；加一项对 base 的 KL 约束，防止遗忘；agent 任务用「单步蒸馏 + 少量完整回合」来控制采样成本 | 学生 2 张卡训练（ZeRO-3），教师（多 LoRA 共用基座）1 张卡提供 logprob，rollout 1 张卡 | 宏平均相对 base 显著提升；每一项都不明显退化 |
| D. 评测 | Base / 各专家 / 融合 / MOPD，统一按接近模型卡的设置：TB2 89 题 × 5 次，128K 上下文，32 并发；SWE 完整 HARD-51，64K 上下文；HLE 用官方 judge；ASI 用 `--sandbox task` | 见第 4 节 | 宏平均提升带置信区间；重复运行波动 |

预计：A 约 1 天，B + C 约 1–1.5 天，D 约 1.5 天。**合计 3–4 天（4×H100）。**

## 4. 为什么需要 4 张 H100 80GB

| 环节 | 估算 | 需求 |
|---|---|---|
| TB2（接近模型卡：128K 上下文，32 并发，平均占用约 50K token） | 4 个数据并行副本，每张卡 8 并发：16GB 权重 + 8 × 50K × 144KB ≈ 58GB KV ≈ 74GB/卡 | **4 × 80GB** |
| SWE（64K 上下文，8 并发） | 16GB + 8 × 64K × 144KB ≈ 88GB | 2 × 80GB（可以和 TB2 分时） |
| MOPD | 学生 8B 训练（ZeRO-3）2 张；教师 logprob 服务 1 张（4 个 LoRA 共用基座，16GB + KV）；rollout 1 张 | 4 × 80GB |
| 专家训练（32K 序列） | 8B LoRA / 全参 + 梯度检查点，单张 60–80GB；4 个专家可以并行 | 4 × 80GB |

本轮只有 1 张 L40S 48GB 加 1 台 GB10，相当于上表需求的约 1/4 到 1/6，而且带宽低。所以评测只能降配：32K 上下文、单次运行、子集。
